## Overview

KittyBot is a modular robotics and telemetry platform being built to explore the systems architecture behind useful small robots: deterministic control, Linux orchestration, communication contracts, simulation support, observability, and local AI-assisted behavior.

The project is intentionally framed as robotics infrastructure rather than a novelty robot. The core question is how to make a robot runtime understandable, testable, and maintainable while it spans hardware, services, state, telemetry, and behavior logic.

## Engineering Problem

Small robotics projects often fail at the boundaries:

- Hardware interfaces are brought up informally and become difficult to reproduce
- Behavior logic outruns the quality of telemetry and diagnostics
- MCU and Linux responsibilities blur until timing bugs are hard to isolate
- Simulation, bench testing, and hardware operation drift apart
- Failures are difficult to explain because state and messages are not observable

KittyBot is designed around those boundaries from the beginning.

## Architecture Direction

### Control Layer

The MCU side owns timing-sensitive behavior:

- Servo and actuator timing
- Sensor acquisition
- Local safety constraints
- Position limits, timeout behavior, and low-level feedback loops

### Orchestration Layer

The Linux side owns flexible runtime behavior:

- State management and behavior orchestration
- Local service coordination
- Telemetry collection and persistence
- Local model or agent integration where useful
- Networked tools and diagnostics

### Communication Layer

The boundary between control and orchestration is treated as an engineering contract:

- Structured command messages for motion primitives and behavior directives
- Structured telemetry messages for sensor data, actuator feedback, and system state
- Timeout handling and range validation at message boundaries
- Simulation-compatible message flows for development without full hardware availability

## Technical Focus

- Modern C++ runtime organization
- Clear MCU/Linux responsibility separation
- Telemetry-first debugging and observability
- Simulation and bench-test paths before full physical behavior
- Hardware bring-up checklists for sensors and actuators
- Local AI workflows constrained by deterministic system boundaries
