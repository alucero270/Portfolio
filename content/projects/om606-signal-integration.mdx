## Overview

This project is a real-world drivetrain and control-system integration effort: fitting a mechanically injected Mercedes OM606 diesel engine into a Ford F-150 platform whose transmission, cluster, diagnostics, and vehicle behavior still expected ECU-managed gasoline-engine signals.

The engineering problem was not simply mechanical fitment. The vehicle needed believable electronic state after the original engine-management assumptions were removed. That required reverse-engineering signal expectations, adapting sensor behavior, validating timing relationships, and debugging across mechanical, electrical, and controller behavior.

## System Problem

The OM606 uses a mechanical injection pump. Once installed, the Ford PCM no longer had normal control over fuel delivery, ignition, crank/cam synchronization, or expected load signals. The rest of the truck still depended on those signals.

Key dependencies included:

- Transmission behavior tied to crankshaft position, RPM, and throttle/load information
- Instrument cluster tachometer behavior tied to valid engine-speed references
- PCM fault-state behavior tied to expected timing and synchronization relationships
- Drivability dependent on stable signal paths during startup, idle, load change, and road use

Without valid adapted signals, the vehicle could lose shift behavior, generate diagnostic faults, lose cluster functionality, or become unreliable to drive.

## Integration Work

### Signal Emulation Layer

Built and refined signal adaptation for:

- **Crankshaft position** - analyzed timing expectations and produced a PCM-compatible engine-speed signal
- **Camshaft synchronization** - provided synchronization behavior to reduce fault states from missing OEM references
- **Throttle/load behavior** - adapted throttle-position behavior so the transmission could infer operating state
- **Tachometer signal** - produced stable RPM output from a mechanically governed engine system

### Debugging and Validation

The validation process followed the actual system behavior instead of assuming bench behavior was enough:

- Observe startup, idle, and road behavior under real conditions
- Check controller fault states after each signal change
- Validate transmission response to throttle/load adaptation
- Trace symptoms from mechanical behavior through wiring and signal interpretation
- Iterate signal timing and routing until stable operation was achieved

### Engineering Framing

This project demonstrates the kind of problem Loose Arrow Labs is being built around: a physical system whose success depends on software-adjacent reasoning, electrical signal behavior, mechanical constraints, and disciplined validation.

The important work is at the boundary: translating one subsystem's reality into another subsystem's expectations without pretending either side is simpler than it is.
